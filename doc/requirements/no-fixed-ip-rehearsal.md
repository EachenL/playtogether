# 需求：无需固定 IP 的小规模远程排练（4–6 人）

状态: 提案
日期: 2026-11-23
关联: [design/architecture.md](../design/architecture.md)（§9 设计债 1/2 与本需求的二期方案重叠）

---

## 背景 / 动机

当前架构（ADR-0002，Hub 混音）要求一台**可达的服务器**：客户端要能主动向它发 UDP，意味着服务器需要公网 IP + 端口开放（固定 IP / 端口转发 / 云主机）。这对"几个朋友想排练"的场景是过重的门槛：

- 没人为一次排练去租 VPS；
- 家庭宽带没有公网 IP（CGNAT 普遍），端口转发不可用；
- 部署 `deploy/` 全家桶（systemd + nginx + webd）对普通用户不现实。

**目标**：4–6 人异地排练，不需要任何固定 IP 的基础设施，延迟仍满足 < 20 ms 预算。

## 用户故事

- 作为**房主（组织排练的人）**，我想在自己电脑上点"开房间"，把一个连接码/链接发到群里，朋友就能加入；
- 作为**乐手**，我想粘贴连接码（或点开链接）即可加入，不需要装额外网络软件、不需要关心路由器配置；
- 作为**房主**，如果我的网络环境无法被直连，我想得到明确的提示和替代指引，而不是无声失败。

## 关键技术事实（方案论证的基础）

1. **Hub 模型下客户端的 NAT 类型无关紧要**。客户端只做两件事：向房主的单一端点发包、从同一端点收回包。回包恰好匹配客户端 NAT 的出站映射 —— 即使客户端在**对称型 NAT / CGNAT** 后也能通。被连的一方才需要"可达性"。
   → **6 人中只需 1 人（房主）网络达标**，且这人是唯一能感知并改善自己网络环境的人。
2. **UDP 打洞的可行性由房主 NAT 类型决定**（若不用 UPnP）：
   - 全锥形（full-cone）：客户端直接发流即可通，零协调；
   - 受限锥形（restricted）：需要房主先向客户端端点发"敲门"包 —— 需要双向候选交换（信令）；
   - 对称型（symmetric）/ CGNAT：STUN 探测到的端口与实际业务端口不一致，直连失败，需 UPnP 或中继兜底。
3. **UPnP / NAT-PMP / PCP** 可让房主路由器自动钉一个外部端口（行为等价于端口转发），家庭路由器支持率可观 —— 这是第一优先尝试，成功则完全绕开 NAT 类型问题。
4. **信令不可避免但可以极简**：房主端点（连接码）的分发可以用群聊粘贴完成（零基础设施）；受限锥形房主的反向敲门需要客户端回传自己的候选，可通过"连接码 + 回执"或极小的信令页解决（见开放问题）。
5. **带宽账**（单声道 48 kHz i16 ≈ 768 kbps/人）：
   - Hub/host 模式 6 人：房主上行 ≈ 5 × 768 k ≈ 3.8 Mbps（回发给每人的混音流）；乐手各 768 k 上/下行。现代家庭宽带无压力，弱上行链路（手机热点）是例外。
6. 网页浏览器**不能发裸 UDP**，网页端的"无服务器"只有 WebRTC（与 ADR-0003 冲突）或"连到房主进程内嵌的 WS 桥"（方案 C 的做法）两条路。

## 候选方案

### A. 云 VPS + 域名（不消除服务器，只降低门槛）

同区域 VPS（几元/月）跑现有 `deploy/` 全套。IP 无所谓"固定"，DNS 指过去即可。
- 优点：零代码改动，成功率 100%，网页端原生支持。
- 缺点：仍是"要有人运维的服务器"；多一跳（乐手→机房→乐手），同城机房延迟尚可。
- 定位：**兜底与大型房间方案**，本需求的主线之外。

### B. Overlay 虚拟局域网（Tailscale / ZeroTier / 自建 headscale）

全员装客户端，获得虚拟 IP；任意一人（房主）本机跑现有 jt-server，大家连虚拟 IP。
- 优点：**零代码**，今天就能用；打洞 + 中继自动兜底；直连路径延迟与 mesh 相当。
- 缺点：全员要装第三方软件、依赖第三方账号/控制面；国内控制面连通性不稳；网页端不可用。
- 定位：**立即可用的过渡方案**，写进 README 即可。

### C. 房主托管模式（推荐，一期）★ → 详细设计见 [design/host-mode.md](../design/host-mode.md)

房主的客户端进程 = Hub 服务器 + jt-webd 桥 + 网页静态页，三位一体。

```
房主 Tauri 应用（host 模式）
 ├─ jt-engine 会话（房主自己也是乐手）
 ├─ Hub 混音循环（从 server/main.rs 抽成库，复用 jt-core::mix_blocks）
 ├─ 内嵌 WS 桥（jt_webd 逻辑移植进 Rust 或内嵌运行）──▶ 网页乐手
 └─ 内嵌 HTTP 静态页：浏览器乐手直接开 http://<房主地址>:<port> 加入
```

连接可达性三档：
1. **UPnP/NAT-PMP/PCP** 请求路由器映射外部 UDP 端口（`rust natpmp`/`igd` 类 crate）；
2. 失败则 **STUN** 探测公网端点（自实现 RFC 5389 binding，百行级），生成**连接码**（`ip:port` 或 base32 编码进 `playtogether://join/xxx`）；
3. 都失败则提示房主走方案 B 或 A，并给出诊断信息（NAT 类型检测结果）。

改动量评估：
- server/main.rs 混音循环 → 抽成 `jt-hub` 或并入 jt-core（逻辑 ~100 行，纯迁移）；
- jt-engine / Tauri 增加 host 模式与"开房间"UI、连接码生成/解析；
- UPnP + STUN 客户端：各一个小 crate 或自实现；
- 网页桥移植为 Rust（axum/tokio-tungstenite）或继续内嵌跑 Python —— 建议顺势 Rust 化，消掉 Python 运行时依赖。

- 优点：零基础设施；客户端 NAT 无关紧要（技术事实 1）；网页端可用（连房主内嵌桥）；房主直连延迟优于云机房。
- 缺点：房主挂了房间就散（对 4–6 人排练可接受）；房主网络必须达标（三档兜底 + 明确诊断缓解）；代码改动中等。

### D. P2P 全互联 mesh + 打洞（二期）→ 详细设计见 [design/p2p-mesh.md](../design/p2p-mesh.md)

每人向其他所有人发流，本地各自混音、各自维护**每流独立抖动缓冲**。
- 优点：延迟理论最优（A↔B 直连一跳）；无单点；每流对齐天然解决设计债 1/2。
- 缺点：每对人都要打洞（对称×对称组合失败，需中继兜底）；信令必须做成常驻功能；每客户端 5 路上行 ≈ 3.8 Mbps；改动大（每流 seq 重排 + 本地混音 + ICE 式协商）。
- 定位：**二期演进**，与架构文档设计债 1/2 是同一批工作，一鱼两吃。

### E. WebRTC（网页端 P2P）

浏览器唯一的原生 P2P 通道，可让网页乐手免服务器直连。但编解码与 jitter buffer 不可控，与 ADR-0001/0003 的核心卖点（裸 PCM + 可解释延迟模型）冲突。
- 定位：仅在"网页用户成为主要群体且拒绝装任何东西"时重开此决策（更新 ADR-0003）。

## 推荐路线（分期）

| 期 | 内容 | 成果 |
|---|---|---|
| 0（本周可做） | README 写入方案 B 用法（Tailscale + 本机 jt-server） | 立即可用 |
| 1 | 方案 C：host 模式 + UPnP/STUN + 连接码 + 内嵌网页桥 | 本需求验收 |
| 2 | 方案 D：mesh + 每流抖动缓冲（连同设计债 1/2） | 延迟与健壮性上限 |

## 验收标准

1. 房主在典型家庭宽带（有公网 IP 或全锥 NAT）上开房间，5 名乐手（含 ≥1 名网页端）用连接码/链接加入，全员可互相听见；
2. 全程无任何固定 IP 服务器参与数据面；
3. 单向延迟估算仍 < 20 ms（同城）；
4. 房主 NAT 不可直连时，客户端给出明确的诊断输出（NAT 类型、UPnP 失败原因）与替代指引，而非静默失败；
5. 房主退出/掉线，其他客户端在 10 s 内感知（复用现有 last_seen 剪除语义）并提示房间已散。

## 开放问题

1. **受限锥形房主的反向敲门**：客户端候选如何回传？倾向"连接码是短码，乐手客户端向一个极小的 rendezvous 上报"或干脆要求 UPnP 成功 —— 需原型期实测 NAT 类型分布后定。
2. **网页桥 Rust 化的时机**：一期内嵌跑 Python（快）还是直接移植（消依赖）？倾向一期直接 Rust 化，host 进程单二进制分发是本方案的 UX 基石。
3. 连接码是否需要防碰撞/加密（当前任何人拿到码即可进房间 —— 房间语义见设计债 4/5）。
