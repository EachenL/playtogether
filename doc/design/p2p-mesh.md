# 设计：方案 D —— P2P 全互联 mesh（两两直连，本地混音）

状态: 提案（二期）

满足需求: [requirements/no-fixed-ip-rehearsal.md](../requirements/no-fixed-ip-rehearsal.md)

## 1. 通俗解释（说人话）

### 这个方案是什么

方案 C 里房主家的客厅是排练室，所有人的声音都要**绕**他家一趟。方案 D 更直接：**6 个人围成一圈，每两个人之间拉一根专属传声筒** —— A 的声音直达 B，不经过任何第三家。每根传声筒的延迟，就是这两个人网络之间的**直达延迟**，这是物理上的下限，没有更快的方案了。

收到 5 根传声筒传来的 5 路声音后，**每个人在自己耳朵边上把 5 路混在一起**（本地混音），自己弹琴自己零延迟监听。

### 代价是什么

天下没有免费的直连：

1. **每两个人都要打通一根管子**。用前台比喻（见 [host-mode.md](host-mode.md) §1）：打洞 = 两人**同时**给对方寄一封信，各自前台的台账上就有了对方，之后双向畅通。但有些前台有怪脾气（对称型 NAT：你每寄一个不同地址就换一个寄件信箱号，朋友按你报的信箱号寄信永远到不了）—— 两个怪脾气前台碰上，这根管子就通不了，得有人中转（§5 兜底）。
2. **每人的上传量变大**：不是发 1 路给房主，而是发 5 路给 5 个人。每人上行 ≈ 5 × 768 kbps ≈ **3.8 Mbps**，现代宽带没问题，弱上传链路会难受。
3. **代码复杂度上台阶**：要管理 5 条独立连接、5 个独立缓冲、每路按序号重排、本地混音 —— 但这恰好是架构文档设计债 1/2 要求做的工作，做了不亏。

### 跟方案 C 怎么配合

方案 D **不取代房主，只是降级房主的职责**：房主从"排练室"降级为"**群主**"—— 大家加群时还是扫他的连接码，但入群后彼此直连，声音不再绕他家。房主掉线？换个人当群主就行，声音不断。

## 2. 架构

```
信令面（低频，字节级流量）                数据面（高频，音频直连）
┌────────┐   候选交换/心跳    ┌────────┐      ╔═════ A ⇄ B 直连 ═════╗
│  房主   │◀────────────────▶│ 乐手 X │  ═══▶║ A ⇄ C  A ⇄ D  ...    ║
│(群主)   │─────────────────▶│ 乐手 Y │      ╚═════ 两两 UDP 直连 ═══╝
└────────┘  转发彼此的候选     └────────┘   （打洞失败的 pair 走房主中继）
```

- **信令面**：复用方案 C 的"开房间/连接码"机制做 rendezvous。乐手入群时把自己的公网候选（STUN 探测）报给房主，房主把"群成员列表 + 各自候选"广播给全员 —— 这就是全部信令，频率是秒级心跳，不是音频流量。
- **数据面**：每对乐手之间独立的 UDP socket 对，直发 JT01。**协议完全不变**（`seq` 字段终于派上用场，见 §3）。
- **混音**：每个客户端本地跑 `jt-core::mix_blocks` 把其余 5 路混成一路播放。混音内核直接复用，零改动。

## 3. 每流独立抖动缓冲（本方案的核心新增件，也是设计债的偿还）

现状（[architecture.md](architecture.md) §4）：单一 `SampleFifo` 样本队列，无序号感知、无重排。mesh 下每人收 5 路，每路网络状况不同，**必须每路一个缓冲**：

```
路 A ──▶ PeerBuf[A] ──┐
路 B ──▶ PeerBuf[B] ──┤   按各自 seq 重排 + 各自适应深度
路 C ──▶ PeerBuf[C] ──┼──▶ mix_blocks(5 路) ──▶ 播放回调
 ...                  │
路 E ──▶ PeerBuf[E] ──┘
```

每个 `PeerBuf`：

1. **按 `seq` 重排**：乱序包按序号归位（协议里的 `seq` 字段为此预留，协议零改动）；
2. **丢包处理**：`seq` 跳号 → 用上一块外推（简单重复）补位，听感是轻微"卡"而非"跳"；
3. **自适应深度**：每路独立估算抖动（到达间隔方差），深抖动路多缓冲、稳路少缓冲 —— 比现在全局固定 `TARGET_DEPTH=128` 更精细，总延迟反而可能更低；
4. **每路延迟可观测**：CLI/UI 显示"到 B 延迟 6 ms、到 C 延迟 22 ms" —— 合奏里谁拖后腿一目了然，这是排练场景的刚需诊断。

**时间对齐**：混音前按各路缓冲深度对齐（慢路多等、快路多缓）—— 直接偿还设计债 1（服务器"最新块"松弛对齐）。

## 4. 打洞流程（每对一遍）

```
1. 房主广播成员列表 {公网候选, 本地候选}
2. 每对 (X, Y) 互发"敲门"包（同时发到对方的公网和本地候选）
3. 敲门包到达 → 双方台账互相登记 → 直连建立
4. 信令确认（经房主）：X 报告"我收到了 Y 的包"，Y 同样报告
   双方都确认 → 数据面切直连
5. 任一方确认失败 / 3 s 超时 → 该 pair 标记为"经房主中继"
```

中继（兜底）：打不通的 pair 走房主转发 —— 即**退回方案 C 的路径**，但只影响这一对，其他人照常直连。所以方案 C 是方案 D 的自然子集：**先实现 C，D 是在 C 之上加直连优化**。

## 5. 带宽与延迟

| 项 | 数值 | 说明 |
|---|---|---|
| 每人上行 | 5 × 768 kbps ≈ 3.8 Mbps | 发给 5 个对端各一路 |
| 每人下行 | 同上 | 收 5 路 |
| A→B 单向延迟 | 直连网络 + 2×块 + 抖动缓冲 | **物理下限**，无第三跳 |
| 房主负载 | 信令字节级 +（兜底时）中继个别 pair | 大幅低于方案 C |

对比方案 C：A 听 B 的路径从"A→房主→B"变成"A→B"，省一跳。6 人同城时差距是几毫秒，跨城时可能差 10–20 ms —— 规模越大、分布越散，D 的收益越明显。

## 6. 改动清单

| 改动 | 位置 | 量级 |
|---|---|---|
| `PeerBuf`（seq 重排 + 丢包外推 + 自适应深度） | jt-engine | **大**（本方案核心工作量） |
| 多路 socket 管理 + 打洞状态机 | jt-engine | 中 |
| 信令消息（成员/候选/确认，走房主） | jt-hub + 协议扩展 | 中 |
| 本地混音（mix_blocks 已有，接线即可） | jt-engine | 小 |
| per-peer 状态展示 | cli / client UI | 小 |
| 中继兜底（复用 C 的 Hub 路径） | jt-hub | 小 |

前置依赖：方案 C（信令/rendezvous/连接码复用）。

## 7. 风险与边界

- **对称×对称 pair 必须中继**：无法消除，只能兜底 + 诊断提示（"你到 XX 的直连失败，经由房主中转，多约 X ms"）。
- **NAT 映射超时**：UDP 台账记录有寿命（几十秒到几分钟），长时间静默会失效 —— 每路需周期保活包（复用 JTPN 心跳即可）。
- **网页乐手**：浏览器不能发裸 UDP，mesh 对网页端不可达 —— 网页用户仍走房主的 WS 桥（方案 C 路径）。若未来网页端成为主体，需重开 WebRTC 决策（ADR-0003）。
- **人数上界**：全互联 pair 数 = n(n-1)/2，6 人 15 对尚可，>8 人不建议 mesh（信令复杂度和每路维护成本上升）—— 大房间回到云 Hub。

## 8. 开放问题

1. `PeerBuf` 自适应深度的算法选型（简单方差阈值 vs. 类似 NetEQ 的延迟-丢包联合优化）。
2. 信令协议形态：复用 UDP + 新消息类型，还是信令走 WS（反正网页桥有 WS）—— 倾向后者，信令与数据面分离。
3. 混音前的时间对齐精度目标：对齐到块级（当前粒度）还是采样级（需要每路重采样/伸缩，复杂度大增）—— 倾向一期块级。
