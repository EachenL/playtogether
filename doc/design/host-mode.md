状态: 提案

## 1. 通俗解释（说人话）

### 这个方案是什么

想象 6 个朋友要排练。**其中一个人（房主）把自家客厅当排练室**：其他 5 人把各自的声音都"寄"到他那里，他把"除你之外所有人的声音"混好，再分别寄回给每个人。现在的系统就是这么工作的，只不过"排练室"以前必须是机房里的服务器 —— 本方案就是**把排练室搬进房主的笔记本电脑**，房主点一下"开房间"，群里发个连接码，大家就能进。

### 为什么不需要固定 IP

先理解你家路由器（NAT）是怎么工作的 —— 它就像**写字楼一楼的前台**：

- 你（内网设备）想对外寄信，必须经前台代寄。前台会在**台账**上记一笔："xx 房间的人往这个地址寄过信"。
- 之后**只有台账上登记过的地址**寄来的信，前台才肯转交给你。陌生人直接寄信？查无记录，拒收。

这就是为什么外面的机器不能"主动"连你家电脑 —— 不是连不上，是前台不放行。

而本方案里，**每个乐手只做两件事：往房主的地址寄信、收房主从同一地址寄回的信**。房主的回信恰好来自乐手登记过的地址，台账一查就放行 —— 所以**乐手家的前台是什么脾气根本无所谓**。

整个系统里只有**房主**需要"能被找到"。而 6 个人里，房主恰好是那个知道自己网络情况、路由器在自己手里、可以想办法的人。我们把"让房主可被找到"做成三档自动兜底（见 §3）。

### 房主的三档兜底，还是用前台打比方

1. **UPnP（自动登记信箱）**：房主的路由器支持的话，程序直接跟前台说好——"以后凡是寄到 9 号信箱的信，一律转交给我"。一劳永逸，什么信都能收。
2. **STUN + 打洞（先寄一封信占位）**：先让一个公共查询服务（STUN）告诉房主"你在外面的门牌是 `1.2.3.4:56789`"，把这个门牌做成连接码发给乐手。乐手往这个门牌寄第一包声音时，房主前台台账上就有了记录，之后回信畅通 —— 前提是房主的前台是"认地址不认人"的宽松型（全锥形 NAT，家庭宽带很常见）。
3. **都失败 → 提示换路**：明确告诉房主"你的网络直连不了，建议全员装 Tailscale 组个虚拟局域网"，而不是无声失败。

### 房主也是乐手

房主的电脑同时干两件事：自己弹琴（正常乐手会话）+ 当排练室（混音回发）。混音时会**排除发送者自己**，所以房主听到的也是"其他 5 人"，本地监听零延迟。

## 2. 架构

```
                 房主的 Tauri 应用（host 模式，单进程）
                 ┌────────────────────────────────────┐
  桌面乐手 ──────▶│  Hub 混音循环（jt-hub 库）          │◀────── 桌面乐手
                 │   ├─ 房主自己的 jt-engine 会话      │
  浏览器乐手 ────▶│  ├─ WS 桥（网页版接入）            │◀────── 浏览器乐手
   (HTTP+WS)     │   └─ 内嵌静态页 http://房主:9100    │
                 └────────────────────────────────────┘
```

- **Hub 混音循环**：现有 `server/src/main.rs` 的循环原样抽成库（`jt-hub` 或并入 jt-core），纯逻辑迁移，协议不变（ADR-0002 语义完全保留）。
- **WS 桥 Rust 化**：`dist-web/jt_webd.py` 的逻辑移植进 host 进程（tokio + tungstenite + 静态页服务），host 变成**单个二进制**—— 这是本方案 UX 的基石：房主下载一个 app 就够了，没有 Python、没有 systemd、没有 nginx。
- **网页乐手**：房主分享的不是连接码而是一个链接 `http://房主地址:端口/`，浏览器打开即是 `dist-web/web/` 现有页面。

## 3. 连接流程

### 3.1 房主侧（开房间）

```
点"开房间"
  1. 绑定 UDP socket（房主+Hub 共用同一 socket，保证回信端口一致 ★）
  2. 试 UPnP/NAT-PMP 映射外部端口 ──成功──▶ 记录外部端点
  3. 失败 → STUN 探测公网端点
  4. 生成连接码（外部端点编码，如 playtogether://join/xxxx）
  5. 内嵌 HTTP+WS 服务开始监听（网页乐手入口）
  ★ 关键细节：Hub 给乐手回包必须从"收到乐手包的同一 socket"发出，
    否则乐手前台的台账对不上、回信会被拒收。
```

### 3.2 乐手侧（加入）

```
粘贴连接码 / 点开链接
  1. 解析出房主端点，connect UDP socket
  2. 直接开始发流（第一包就是"敲门"，同时在房主前台登记）
  3. 收到房主回包 = 连接成功；2 秒无回包 = 提示失败原因
```

### 3.3 失败诊断（验收标准 4 的落地）

房主侧在开房间时顺带做 NAT 行为检测（STUN 双请求比对端口），结果写进"房间诊断"面板：

| 检测结果 | 提示 |
|---|---|
| UPnP 映射成功 | ✓ 完全可达 |
| 全锥形 NAT | ✓ 直连可用 |
| 受限锥形 NAT | ⚠ 乐手需先敲门（一期先提示走 Tailscale，见开放问题） |
| 对称型 / CGNAT | ✗ 无法直连，建议 Tailscale 或方案 A（云 VPS） |

## 4. 改动清单

| 改动 | 位置 | 量级 |
|---|---|---|
| 混音循环抽库 | `server/src/main.rs` → `jt-hub`（或 jt-core 内模块） | 小（~100 行纯迁移） |
| host 会话（房主 = 乐手 + Hub） | `jt-engine` 或 client | 中 |
| UPnP / NAT-PMP | 引 `igd` / `natpmp` crate | 小 |
| STUN 客户端 | 自实现 RFC 5389 binding（~百行）或引 crate | 小 |
| WS 桥 + 静态页 Rust 化 | host 进程内 tokio 服务 | 中 |
| 连接码生成/解析 | 新模块（端点编解码） | 小 |
| "开房间" UI + 诊断面板 | client 前端 | 中 |
| CLI host 模式 | `jt-cli --host` | 小（复用上面的库） |

## 5. 带宽与延迟

- 房主上行：5 × 768 kbps ≈ **3.8 Mbps**（回发 5 路混音）+ 下行同量级。现代家庭宽带无压力；房主用手机热点开房是反模式，诊断面板应检测并警告。
- 延迟：乐手 A → 房主 → 乐手 B，两跳直达；同城下优于绕云机房。乐手↔房主的抖动缓冲、块延迟不变（复用 jt-engine 现有管线）。

## 6. 风险与边界

- **房主单点**：房主掉线房间即散（4–6 人排练可接受；客户端 10 s 内感知并提示，复用现有 `last_seen` 剪除语义）。
- **房主机器负载**：6 人混音单线程每包 O(n)，现有实现即可支撑；CPU 瓶颈在人数 > 10 时才需要考虑（那是云服务器的事）。
- **连接码无鉴权**：拿到码即可进房（设计债 4/5 的房间语义问题独立推进）。

## 7. 开放问题

1. 受限锥形房主的反向敲门：一期是否支持？候选做法是"连接码 + 乐手回执"或要求 UPnP 成功——建议原型期先实测 NAT 分布再定。
2. 连接码是否编码进 URL scheme（`playtogether://join/xxx`）以支持桌面端点链接直接唤起。
